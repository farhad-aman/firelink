# Giving firelink to other people — design

Date: 2026-08-10
Status: approved, not yet planned

## The problem

Installing firelink today reads:

```bash
brew install aria2
git clone https://github.com/farhad-aman/firelink.git
cd firelink && make install
```

Three commands, one of which leaves a clone the person has to keep. `ffmpeg`
is not mentioned at all — it is discovered later, when a YouTube download
above 360p fails at the merge step. Updating means remembering where the clone
went and running `git pull && make install` inside it.

That is a reasonable arrangement for the author and an unreasonable one for a
friend. The goal is one command to install, and updates that arrive through
the `brew upgrade` they already run.

## Audience and constraints

**Every recipient is on macOS with Homebrew.** Established 2026-08-10. No
Linux, no Windows, no Homebrew-less Mac. This is what makes a tap the obvious
answer rather than one option among several.

**firelink needs two binaries it does not ship.** `aria2c` for every download,
`ffmpeg` for any YouTube merge above 360p and for subtitle burn-in. Any
install story that does not deliver these has not solved the problem, because
these are the parts a friend cannot debug.

**firelink imports `yt_dlp` as a library, not only as a binary.**
`dl/ytdlp.py:25` imports `gen_extractor_classes`, and `:90` imports
`yt_dlp.version`. The extractor lookup that decides whether a URL belongs to
yt-dlp or to aria2 rests entirely on that import. If `yt_dlp` is not importable
inside firelink's own environment, `_load()` returns `[]`, `handles()` answers
False for every non-YouTube address, and those downloads silently become aria2
saving an HTML page. Nothing raises.

That constraint is the sharpest one in this document. It rules out the
otherwise attractive shape of `depends_on "yt-dlp"` and letting the formula
supply only the binary.

## The decision

A Homebrew tap, `farhad-aman/homebrew-tap`, holding one formula. Versions ship
as git tags; a GitHub Action rewrites the formula so releases reach people
without manual editing.

The tap is a second public repository that does not exist yet and must be
created. Homebrew requires the name to begin with `homebrew-`, which is what
lets it be referred to as `farhad-aman/tap`.

### What a friend types

```bash
brew install farhad-aman/tap/firelink
```

That pulls `aria2`, `ffmpeg` and `python@3.13` as dependencies, builds a sealed
virtualenv, and puts `dl` on their PATH.

```bash
brew upgrade            # firelink rides along with everything else
brew uninstall firelink # leaves nothing behind
```

A bare `brew upgrade` reaches firelink: Homebrew upgrades outdated formulae
from third-party taps exactly as it does core ones. Two caveats, neither
serious. Homebrew refreshes tap metadata via an implicit `brew update` only
once per `HOMEBREW_AUTO_UPDATE_SECS`, default 86400 (verified against Homebrew
6.0.15), so someone upgrading within a day of a release may need one explicit
`brew update` first. And a formula somebody has `brew pin`ned is skipped.

## The formula

```ruby
class Firelink < Formula
  include Language::Python::Virtualenv

  desc "Terminal download manager over aria2c"
  homepage "https://github.com/farhad-aman/firelink"
  url "https://github.com/farhad-aman/firelink/archive/refs/tags/v0.2.0.tar.gz"
  sha256 "<computed at release>"
  license "MIT"

  depends_on "aria2"
  depends_on "ffmpeg"
  depends_on "python@3.13"

  # generated by `brew update-python-resources`, never hand-written
  resource "..." do
    url "..."
    sha256 "..."
  end

  def install
    virtualenv_install_with_resources
  end

  test do
    assert_match version.to_s, shell_output("#{bin}/dl --version")
  end
end
```

`virtualenv_install_with_resources` builds one sealed environment containing
firelink and every Python dependency, yt-dlp among them. That satisfies the
library-import constraint above without any special plumbing, and it keeps
`ytdlp._bundled()` correct unchanged: that function looks for a `yt-dlp`
beside `sys.executable`, and the virtualenv puts one exactly there.

The roughly two dozen `resource` blocks are machine-generated. They are never
edited by hand, in this design or afterwards.

## Changes inside firelink

### `pyproject.toml` — a console script

```toml
[project.scripts]
dl = "dl.__main__:main"
```

`main(argv=None) -> int` already exists at `dl/__main__.py:80`, so this needs
no new code. It is what makes `virtualenv_install_with_resources` emit a `dl`
executable, sparing the formula a hand-written shim. It also makes
`uv tool install` and `pipx` work for anyone off Homebrew, at no cost.

The existing `make install` shim lives at `~/.local/bin/dl` and is unaffected.

### `pyproject.toml` — the licence *(done)*

`license = "MIT"`, `license-files = ["LICENSE"]`, and a `LICENSE` file at the
repo root. `license-files` is PEP 639, understood by setuptools from 77.0, so
`build-system.requires` moved from `>=68` to `>=77`.

Homebrew formulae declare a licence, and people are about to redistribute this
by tapping it. Verified: metadata accepted, 1812 tests still pass.

### `dl/ytdlp.py` — advice that matches the install

`staleness_advice()` currently ends with ``run `make install` ``. For a
brew-installed copy that sends the person somewhere with no clone, and it fires
at precisely the moment their YouTube downloads have started failing — the
worst time to be given a useless instruction.

```python
def _brew_installed() -> bool:
    return "/Cellar/" in sys.prefix


def staleness_advice() -> str:
    days = age_days()
    if days is None or days < STALE_DAYS:
        return ""
    remedy = "brew upgrade firelink" if _brew_installed() else "make install"
    return f"yt-dlp is {days} days old — sites break silently; run `{remedy}`"
```

Homebrew installs into `$(brew --prefix)/Cellar/firelink/<version>/libexec`,
so `sys.prefix` is a reliable marker. The function's docstring also claims
`brew upgrade` cannot reach firelink's yt-dlp; for a tap install that is no
longer true, and it needs rewriting.

### `dl/__main__.py` — `dl --version`

Prints the installed version and exits 0, read from package metadata rather
than from a second hardcoded constant:

```python
from importlib.metadata import PackageNotFoundError, version
```

falling back to `"unknown"` when the package is not installed as a
distribution, which is the case when running from a checkout. It gets a line
in `USAGE`.

This exists because "which version are you on" is the first question of every
bug report, and today neither party can answer it. It also makes a sharper
formula smoke test than `dl --help`: matching the version proves the package
metadata installed correctly, not merely that argparse runs.

### Version numbering

`pyproject.toml` says `0.1.0` and has never been bumped. From here the version
and the git tag must agree, or `dl --version` lies and the formula's test block
fails. The release workflow asserts they match and refuses to publish
otherwise. First tagged release: `v0.2.0`.

## Release automation

`.github/workflows/release.yml` in the firelink repo, on `push` of a `v*` tag,
running on a macOS runner because it needs Homebrew:

1. Assert `pyproject.toml`'s version equals the tag, or fail the run.
2. Compute the sha256 of GitHub's source tarball for the tag.
3. Check out the tap repo using a token.
4. Rewrite `url` and `sha256` in `Formula/firelink.rb`.
5. Run `brew update-python-resources firelink` to regenerate every `resource`
   block from `pyproject.toml`.
6. Commit and push the tap.

**One setup step only the author can perform:** a fine-grained PAT with
`contents: write` on `homebrew-tap`, stored as a secret named `TAP_TOKEN` in
the firelink repo. Without it step 3 cannot write.

Steps 2 through 6 are also documented as a manual sequence, so a release is
still possible when the Action is broken or GitHub is unreachable.

**The one unverified assumption in this design is step 5.**
`brew update-python-resources` resolves a formula's Python dependency tree, and
it is built around formulae whose main package lives on PyPI. firelink does
not, and its `url` is a GitHub tarball. Whether the command handles that is
unconfirmed. The implementation must test it on the real formula before the
workflow is written, and fall back to generating the resource blocks directly
from `pyproject.toml`'s dependency list if it does not. Every other step is
ordinary shell work.

## README

The install section leads with the brew command. The current clone-and-`make
install` moves down to a "From source" subsection, which is now what it
actually is: the author's path, not the user's. Update and uninstall get named
explicitly, since "how do I update" is the question this work exists to stop
answering.

## Verification

Formula mistakes do not show up in unit tests, so most of this is real
installs:

- `brew audit --strict --new firelink` — catches what Homebrew already knows
- `brew install --build-from-source farhad-aman/tap/firelink` on the author's
  machine, before any friend is told the tap exists
- `brew test firelink` — runs the formula's test block
- a real download through the brew-installed `dl`, **including one non-YouTube
  URL**, because that is the only thing that proves `yt_dlp` is importable
  inside the sealed virtualenv and the extractor routing survived packaging. A
  green test suite cannot show this; the failure mode is silent.

The Python changes get ordinary unit tests: staleness advice names brew under a
Cellar prefix and `make install` otherwise; `dl --version` prints the
distribution version and returns 0.

## What this does not solve

- **yt-dlp staleness between releases.** A sealed virtualenv means a friend's
  yt-dlp is as old as the last tag, and yt-dlp breaks when sites change. The
  corrected advice text tells them to upgrade. A scheduled monthly resource
  bump is possible later; it is deliberately not in this design.
- **Hard subtitles.** Homebrew's `ffmpeg` is built without libass, so burn-in
  still fails. Unchanged, and already documented in the README.
- **Network conditions.** The formula downloads from github.com. If that is
  slow or blocked for a recipient, nothing here helps.
- **What is on `main`.** Friends receive tags. Unreleased work does not reach
  them, which is the point.

## Alternatives rejected

**Thin formula, `pip install` at install time.** Smallest formula and the
freshest possible yt-dlp. Rejected: Homebrew forbids network access during
install, `brew audit` fails it, it breaks when PyPI is slow, and it is exactly
the bare-pip path that dropped `yt-dlp-ejs` and silently broke every YouTube
download on 2026-08-08.

**`uv tool install git+https://…`.** Nearly no packaging work and always
tracks git. Rejected: it installs neither aria2 nor ffmpeg, leaving friends
with two brew commands and a README — it solves the Python half, which was
already the easy half.

**A HEAD-tracking formula.** No release process at all. Rejected: friends would
need `brew upgrade --fetch-HEAD firelink`, a bare `brew upgrade` would skip it
entirely, and a bad merge would reach everyone immediately.

**`depends_on "yt-dlp"` for the binary.** Fewer resources to maintain and
yt-dlp stays fresh with `brew upgrade`. Rejected on the library-import
constraint above: it would silently disable extractor routing for every
non-YouTube site.
